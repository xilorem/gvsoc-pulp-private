1. The big picture

GVSOC is a virtual platform: software models stand in for hardware blocks, and a discrete-event engine decides when their actions happen. A component might model a processor, memory, interconnect, DMA, UART, or a testbench pretending to be the hardware around the device under test.

The first concept to lock in is that a typical GVSOC model has two halves:

Python Structure and configuration

Creates instances, gives them parameters, exposes ports, and binds the components into a system. Think “schematic plus build description.”

C++ Runtime behavior

Receives requests, changes state, schedules future work, produces responses, and decides when a test finishes. Think “what this block does over simulated time.”

The shortest useful mental model: Python builds a graph. C++ runs the graph. Interfaces are the graph's edges. The simulation engine orders events in virtual time.

From source files to a running simulation

Python targetconstructs the tree
→
Generated configcomponents, properties, bindings
→
Buildengine + model shared libraries
→
RunC++ callbacks and events
→
Exit statuspass or fail

The engine itself is generic. The target tells it which system to instantiate. Compiled C++ models are loaded as shared libraries, and their Python descriptions tell GVSOC how to configure and connect them.

2. The actual Reg32_3dDma model

The model discussed here is not the newer idma_v2 model. It is the legacy, IO-v1, register-programmed model whose Python entry point is pulp/idma/reg32_3d_dma.py. Its C++ top is pulp/idma/reg32_3d_dma.cpp.

What the Python wrapper builds

Reg32_3dDma compiles six C++ implementation files into one loadable GVSOC component:

self.add_sources([
    'pulp/idma/reg32_3d_dma.cpp',       # top-level composition
    'pulp/idma/fe/idma_fe_reg32_3d.cpp',# register front end
    'pulp/idma/me/idma_me_3d.cpp',      # 1D/2D/3D decomposition
    'pulp/idma/be/idma_be.cpp',         # generic data mover
    'pulp/idma/be/idma_be_axi.cpp',     # external-memory protocol
    'pulp/idma/be/idma_be_tcdm.cpp',    # local-memory protocol
])

These are not six separately bound system-tree components. They are cooperating C++ vp::Block objects inside one vp::Component. The top constructor gives each layer direct C++ pointers to the next and previous layers:

Reg32_3dDma::Reg32_3dDma(vp::ComponentConf &config)
    : vp::Component(config),
      fe(this, &this->me),
      me(this, &this->fe, &this->be),
      be_axi_read(this, "axi_read", &this->be),
      be_axi_write(this, "axi_write", &this->be),
      be_tcdm_read(this, "tcdm_read", &this->be),
      be_tcdm_write(this, "tcdm_write", &this->be),
      be(this, &this->me,
         &this->be_tcdm_read, &this->be_tcdm_write,
         &this->be_axi_read, &this->be_axi_write)
{}

Requests and data move left-to-right. Acknowledgments move right-to-left. That reverse completion path is what eventually increments DONE_ID.

There are several different queue limits because they model different pipeline stages. A descriptor slot, middle-end queue entry, logical burst slot, and individual AXI write request are not the same object.

The front end: registers become an IdmaTransfer

Each control port owns its own descriptor registers, so two cores can prepare descriptors without overwriting each other. Ticket counters belong to streams and are shared across ports.

RegisterOffset in this testRole
CONF0x000Selects dimensional behavior. The current model chooses TCDM versus AXI from addresses.
NEXT_ID[0]0x00cReading it launches the programmed descriptor and returns its ticket.
DONE_ID[0]0x014Returns the last completed ticket for stream 0.
DST_ADDR0x0d0Destination base address.
SRC_ADDR0x0d8Source base address.
LENGTH0x0e0Bytes in one contiguous line.
Stride/repetition registers0x0e8–0x110Describe the second and third dimensions.

With multireg_count=2, the bases are calculated as follows:

status_base  = 0x004
next_id_base = status_base  + 4 * 2 = 0x00c
done_id_base = next_id_base + 4 * 2 = 0x014

This parameter must match the register package and software header. Other iDMA revisions reserve sixteen multireg entries and place these registers elsewhere.

On a NEXT_ID read, enqueue_copy() snapshots the port registers into a heap-allocated IdmaTransfer, assigns the stream's next ticket, increments the pending count, and queues the transfer. Tickets start at 1; DONE_ID starts at 0.

The middle end: dimensions become line transfers

The 3D middle end normalizes all shapes into the same loop:

  • A 1D copy is one line in one page.
  • A 2D copy is several lines in one page, advancing by the second-dimension strides.
  • A 3D copy is several 2D pages, also advancing by the third-dimension strides.

For every line it allocates a child IdmaTransfer, points child->parent at the original descriptor, and increments parent->nb_bursts. Once every line has been emitted, it sets parent->bursts_sent = true. The parent completes only when all child transfers have also been acknowledged.

The generic backend: addresses choose protocols

IDmaBe::get_be_consumer() classifies a whole range as local only when it fits completely inside [loc_base, loc_base + loc_size):

bool is_loc = base >= loc_base
    && base + size <= loc_base + loc_size;

return is_loc
    ? (is_read ? loc_be_read : loc_be_write)
    : (is_read ? ext_be_read : ext_be_write);

It then asks both selected protocol backends for a legal burst size. The smaller answer wins. It queues a read burst at the source and a matching write burst at the destination. As source data arrives, IDmaBe::write_data() forwards it to the destination backend.

The TCDM backend: a source of fixed-width chunks

The TCDM backend splits a logical burst into aligned requests no wider than tcdm_width. In this test the width is 32 bytes, so a 48-byte line is read as 32 + 16 and a 64-byte line as 32 + 32. The fake TCDM answers synchronously, so these buffers immediately flow into the AXI write backend.

The AXI write backend: two levels of request

This distinction is essential to understanding the bug:

  1. Logical burst descriptor: a statically allocated IoReq taken from free_bursts. It reserves capacity and stores the destination base and total remaining burst size.
  2. Data-chunk request: a dynamically allocated IoReq created for each chunk arriving from TCDM. This is the request actually sent through axi_write.

Thus one 48-byte logical AXI burst can produce two externally visible writes of 32 and 16 bytes. The logical slot must remain occupied until both chunk responses have been received.

3. One 48-byte descriptor's complete journey

Follow the first test descriptor, which copies 48 bytes from 0x10000000 (local) to 0x20000000 (external).

  1. The tester programs registers. It writes CONF, destination, source, and length through ctrl_0.
  2. A read launches it. Reading NEXT_ID[0] snapshots the registers and returns ticket 1.
  3. The front end queues a parent. It creates one parent IdmaTransfer and records stream 0 in its free-form data vector.
  4. The middle end emits one line child. This is a 1D descriptor, so the line child is also 48 bytes. The parent now has one outstanding child.
  5. The generic backend selects directions. Source is inside the local range, so it selects tcdm_read. Destination is outside it, so it selects axi_write.
  6. A logical AXI burst slot is reserved. The AXI backend queues a 48-byte descriptor in both its data-order queue and acknowledgment queue.
  7. TCDM supplies chunk A32. A synchronous 32-byte read buffer is passed to AXI, producing the first pending external write request.
  8. TCDM supplies chunk A16. The final 16 bytes produce a second pending external write request.
  9. The external target responds. For each response, AXI calls be->ack_data(..., chunk_size), which reduces the child transfer's ack_size.
  10. The child completes. When ack_size becomes zero, the generic backend acknowledges the child to the middle end.
  11. The parent completes. The middle end decrements parent->nb_bursts. Because every child was sent and none remains, it acknowledges the parent to the front end.
  12. Software-visible completion advances. The front end increments DONE_ID, decrements the stream's pending count, deletes the parent, and broadcasts the event wire.

Important: bytes can already be present in destination memory before the descriptor is architecturally complete. Completion requires the AXI responses to propagate all the way back to the front end and advance DONE_ID.

4. The former burst-accounting vulnerability and its fix

The vulnerable AXI backend maintained a FIFO named pending_bursts_ack containing logical burst descriptors waiting for all their chunk responses. But a dynamic write request stored only its parent IdmaTransfer:

req->arg_alloc();
*req->arg_get(0) = (void *)transfer;

It did not store which logical burst descriptor owned that request. When any write response arrived, write_handle_req_end() unconditionally charged its byte count to the front of the FIFO:

vp::IoReq *burst = this->pending_bursts_ack.front();
burst->set_size(burst->get_size() - req->get_size());

if (burst->get_size() == 0)
{
    this->pending_bursts_ack.pop();
    this->free_bursts.push(burst);
}

That logic is valid only if write responses arrive in exactly the same order as their requests. The IO-v1 asynchronous callback supplies the original request pointer, so out-of-order completion is observable—but the implementation throws away the request-to-logical-burst association it needs.

How the test corrupts the FIFO accounting

Call the 48-byte logical burst A and the 64-byte logical burst B. TCDM width 32 creates these requests:

Request index:  0      1      2      3
Request:       A32    A16    B32    B32
Response order forced by test: 0, 2, 1, 3
ResponseWhat should happenWhat the old code does
A32A has 16 bytes remaining.Front is A; A becomes 16. Still correct.
B32B has 32 bytes remaining.Front is still A; subtracting 32 from unsigned 16 underflows to a huge value.
A16A reaches zero and frees its slot.A's corrupted huge counter is reduced, but never reaches zero.
B32B reaches zero and frees its slot.The code still charges A. B remains untouched behind it.

The queue has two slots. A's slot is never freed because its counter underflowed; B's slot is never reached because A remains at the front. Both logical burst slots leak. The third descriptor cannot reserve an AXI burst, even though all four data writes have reached the fake destination memory.

This is why the observed state is done_id=2, AXI requests=4. The first two descriptors have produced all four external writes, but completion bookkeeping prevents the pipeline from freeing capacity for the third descriptor. The failure is progress/accounting, not necessarily destination-data corruption.

The invariant restored by the fix

Every AXI write response must decrement the remaining-byte count of the logical burst that created that particular request. The corrected model stores that association in a second request argument:

// When emitting the AXI write request
req->arg_alloc(2);
*req->arg_get(0) = (void *)transfer;
*req->arg_get(1) = (void *)burst;

// When its response arrives
vp::IoReq *burst = (vp::IoReq *)*req->arg_get(1);
burst->set_size(burst->get_size() - req->get_size());

The completed burst is returned directly to free_bursts; no ordered acknowledgment FIFO is needed. Initializing each dynamic request with init() also establishes a clean argument stack before the two private slots are reserved. Response order can now differ from request order without changing ownership.

6. The Python system tree

A Python generator is declarative in spirit: it says what exists, how it is configured, and how it is wired. Its execution constructs an object tree that GVSOC turns into runtime configuration.

A leaf wrapper

The testbench wrapper in test.py associates a Python component with test.cpp and advertises its ports:

class IDmaInterleavingTester(gvsoc.systree.Component):
    def __init__(self, parent, name):
        super().__init__(parent, name)
        self.add_sources(['test.cpp'])

    def o_CTRL(self, itf):
        self.itf_bind('ctrl', itf, signature='io')

    def i_AXI(self):
        return gvsoc.systree.SlaveItf(self, 'axi', signature='io')

add_sources makes this a leaf backed by C++. The names ctrl and axi must exactly match the strings passed to new_master_port and new_slave_port in C++.

A composite test system

class Testbench(gvsoc.systree.Component):
    def __init__(self, parent, name=None):
        super().__init__(parent, name)

        clock = vp.clock_domain.Clock_domain(
            self, 'clock', frequency=100_000_000)
        idma = Reg32_3dDma(self, 'idma', burst_queue_size=2, ...)
        tester = IDmaInterleavingTester(self, 'tester')

        clock.o_CLOCK(idma.i_CLOCK())
        clock.o_CLOCK(tester.i_CLOCK())
        tester.o_CTRL(idma.i_CTRL(0))
        idma.o_TCDM(tester.i_TCDM())
        idma.o_AXI(tester.i_AXI())
        idma.o_EVENT(0, tester.i_EVENT())

This creates three siblings: a clock, the iDMA device under test, and the tester. The last four lines are the wires in the virtual schematic.

Properties and constructor parameters

Python constructor arguments normally become component properties. Those properties reach the compiled model through its configuration. This is how a single model can represent memories of different sizes or iDMA instances with different queue depths.

# Python wrapper
self.add_properties({'size': size, 'width_bits': width_log2})

// C++ model
js::Config *config = this->get_js_config();
this->size = config->get_child_int("size");

Useful reading rule: when you encounter a mysterious C++ configuration value, search its Python wrapper. When you encounter a Python port name, search the C++ constructor for the same string.

7. The C++ component model

A behavioral leaf usually inherits from vp::Component. It owns state, interface objects, and events.

class IDmaInterleavingTester : public vp::Component
{
public:
    IDmaInterleavingTester(vp::ComponentConf &config);
    void reset(bool active) override;

private:
    static vp::IoReqStatus axi_req(vp::Block *, vp::IoReq *);
    static void step_handler(vp::Block *, vp::ClockEvent *);

    vp::IoMaster ctrl_itf;
    vp::IoSlave axi_itf;
    vp::ClockEvent step_event;
};

The constructor registers ports and attaches callbacks:

IDmaInterleavingTester::IDmaInterleavingTester(vp::ComponentConf &config)
    : vp::Component(config),
      step_event(this, &IDmaInterleavingTester::step_handler)
{
    this->new_master_port("ctrl", &this->ctrl_itf);

    this->axi_itf.set_req_meth(&IDmaInterleavingTester::axi_req);
    this->new_slave_port("axi", &this->axi_itf, this);
}

Callbacks are static because the interface needs a plain function entry point. GVSOC passes the owning block as the first argument; the callback casts it back:

vp::IoReqStatus IDmaInterleavingTester::axi_req(
    vp::Block *__this, vp::IoReq *req)
{
    auto *_this = (IDmaInterleavingTester *)__this;
    // Use _this to access component state.
}

The factory function

Every loadable leaf exposes a C-linkage factory. The loader calls it to create the C++ instance:

extern "C" vp::Component *gv_new(vp::ComponentConf &config)
{
    return new IDmaInterleavingTester(config);
}

If the Python source is found and compiled but the runtime cannot instantiate it, check the factory, model build/install output, and whether the Python/C++ port names agree.

8. Ports and interfaces

Components never reach into each other's internal fields. They communicate through bindings between a master and a slave. Each binding has a signature: the operations and types allowed on it.

SignatureTypical useC++ pair
ioMemory-mapped reads and writesvp::IoMaster → vp::IoSlave
wire<bool>State or event notificationvp::WireMaster<bool> → vp::WireSlave<bool>
clockAssociating components with a clock domainClock master → clock slave

Direction is about who initiates

The labels “input” and “output” can be misleading unless you ask: who calls whom?

  • The tester's ctrl_itf is a master because the tester initiates register requests to iDMA.
  • The tester's tcdm_itf is a slave because iDMA initiates reads from local memory.
  • The tester's axi_itf is a slave because iDMA initiates writes to AXI memory.
  • The tester's event_itf is a slave because iDMA emits completion notifications.

Python and C++ must describe the same interface

PythonC++
self.itf_bind('ctrl', itf, signature='io')new_master_port("ctrl", &ctrl_itf)
SlaveItf(self, 'axi', signature='io')new_slave_port("axi", &axi_itf, this)
SlaveItf(self, 'event', signature='wire<bool>')new_slave_port("event", &event_itf, this)

A name mismatch, signature mismatch, missing callback, or master-to-master connection is a structural bug. It usually fails during generation, binding, or startup—not deep into the test.

9. Time, clocks, events, and reset

GVSOC is event-driven. A model should do a bounded amount of work in a callback and schedule another event when work belongs in the future. It should not sleep in real time or spin in a polling loop.

Clock events

// Declared as state
vp::ClockEvent response_event;

// Connected to its callback in the initializer list
response_event(this, &IDmaInterleavingTester::response_handler)

// Run the callback one cycle from now
this->response_event.enqueue(1);

enqueue(N) schedules the event after N cycles of the component's clock domain. is_enqueued() helps avoid accidentally scheduling the same event twice. this->clock.get_cycles() reports the current cycle count.

Reset has two phases

The framework calls reset(true) when reset is asserted and reset(false) when it is released. Models commonly clear state on assertion and start activity on release. The iDMA tester initializes its memory and starts its events after release:

void IDmaInterleavingTester::reset(bool active)
{
    if (!active)
    {
        // Fill deterministic input memory.
        ...
        this->step_event.enqueue(1);
        this->timeout_event.enqueue(200);
    }
}

A timeout is part of a good test, not just a convenience. Without it, a deadlocked model can leave CI running indefinitely. A timeout should explain the last observed state.

10. Memory-mapped IO requests

The iDMA model in this regression uses the legacy v1 IO protocol. New GVSOC models may use IO v2, so always check the included header and wrapper signature before copying a pattern.

Building a request

vp::IoReq req;
req.prepare();
req.set_addr(offset);
req.set_size(sizeof(value));
req.set_is_write(is_write);
req.set_data((uint8_t *)&value);

vp::IoReqStatus status = this->ctrl_itf.req(&req);

An IoReq describes an address, byte count, direction, and data buffer. The request travels through the bound master port and invokes the remote slave callback.

The four important v1 outcomes

StatusMeaningWhat happens next
IO_REQ_OKAccepted and completed synchronously.The caller can use read data or regard the write as complete immediately.
IO_REQ_INVALIDThe request is not valid for this target.The access fails synchronously.
IO_REQ_PENDINGAccepted, but completion will arrive later.The slave retains the request pointer and eventually calls resp(req).
IO_REQ_DENIEDNot granted yet, often because a queue is full.The target later grants it through the v1 grant handshake.

Synchronous target

The fake TCDM memory completes accesses inside its callback:

if (req->get_is_write())
    memcpy(&local_memory[address], req->get_data(), size);
else
    memcpy(req->get_data(), &local_memory[address], size);

return vp::IO_REQ_OK;

Asynchronous target

The fake AXI endpoint accepts the data but deliberately postpones acknowledgment:

memcpy(&axi_memory[address], req->get_data(), size);
pending_responses.push_back(req);
response_sent.push_back(false);
response_event.enqueue(1);
return vp::IO_REQ_PENDING;

A later event completes one chosen request:

vp::IoReq *req = pending_responses[index];
response_sent[index] = true;
req->get_resp_port()->resp(req);

Critical lifetime rule: after returning PENDING, the request and its data must remain valid until the response. After resp(req), assume the initiator may immediately reuse or destroy it. Never respond twice.

Latency is not the same as pending

A synchronous target can add modeled latency to a request and still return OK. That tells the initiator how long the operation took in its timing model. PENDING is different: it means the response itself will arrive through a later callback.

12. Anatomy of this standalone model test

A compact test directory generally has four jobs, often represented by these four files:

FileQuestion it answers
test.pyWhich models exist, how are they configured, and how are they connected?
test.cppWhat stimulus is sent, how does the fake environment behave, and what counts as success?
MakefileHow can this test be built and run through the common test machinery?
testset.cfgHow does the suite discover, schedule, and judge the test?

Why this is a model-level test

The failure lives in IDmaBeAxi, below MAGIA SDK software and FIFO APIs. Reproducing it with an application, CPU, complete chip, runtime, and real memory hierarchy would add many unrelated failure modes. This test replaces that environment with one small C++ component while preserving every public iDMA boundary involved in the bug:

  • Register requests enter through ctrl_0.
  • Source bytes leave through tcdm_read.
  • Destination writes leave through axi_write.
  • Completion is observed through DONE_ID and the event port.

The tester is therefore both the “software driver” and the “memory system” around the DUT:

Register driverprograms descriptors
→
iDMA DUTmoves and tracks data
→
Fake memoriesTCDM immediate; AXI reordered

The port directions are deliberately reversed

The DUT's control port is a slave, so the tester needs a control master. The DUT's memory ports are masters, so the tester exposes memory slaves. This is why the tester's Python wrapper has o_CTRL() but i_TCDM() and i_AXI().

Qualities of a strong regression

  • Uses the device's public ports and registers instead of internal implementation fields.
  • Creates the smallest configuration that makes the bug deterministic.
  • Checks architectural behavior, not an incidental log line from inside the DUT.
  • Has a bounded timeout with useful failure context.
  • Returns process status 0 only on success.
  • Fails before the fix and passes after it.
  • Keeps unrelated SDK or application layers out of a model-level bug reproduction.

13. Walking through the iDMA regression

The bug is not “DMA copies bad bytes.” It is bookkeeping corruption when asynchronous AXI write responses return in an order different from request issue order. The test therefore needs an AXI endpoint that can retain several requests and respond to them individually in a chosen order.

The controlled setup

  • The local side is a synchronous byte array.
  • The AXI side accepts writes asynchronously.
  • The iDMA has only two burst slots, making leaked accounting visible quickly.
  • Three descriptors are submitted. The third proves the first two truly release their slots.
  • The test polls the public DONE_ID register and verifies copied data.

Why every test.py parameter was chosen

transfer_queue_size4Avoids middle-end capacity becoming the reason descriptor 3 waits.

local_memory64 KiB deterministic source bytes exposed as synchronous TCDM.
axi_memory64 KiB destination initialized to 0xa5, updated when AXI writes are accepted.
pending_responsesStable list of AXI IoReq* objects retained after returning PENDING.
response_sentParallel flags preventing a response from being sent twice.
step_eventSubmits descriptors and polls DONE_ID once per cycle.
response_eventSelects and completes one pending AXI write per cycle.
timeout_eventTurns lack of progress at cycle 200 into a clear failing exit.

Reset starts three independent activities

After reset deassertion, the source memory is filled with a reproducible byte pattern. The descriptor/polling FSM begins at cycle +1, and the deadline is armed for cycle +200. The response FSM is started lazily by the first AXI request, so it cannot run before there is something to acknowledge.

How register programming imitates software

uint32_t IDmaInterleavingTester::submit(
    uint32_t src_offset, uint32_t dst_offset, uint32_t size)
{
    write(IDMA_CONF, 0);                         // 1D
    write(IDMA_DST, AXI_BASE + dst_offset);      // external
    write(IDMA_SRC, LOCAL_BASE + src_offset);    // local
    write(IDMA_LENGTH, size);
    return read(IDMA_NEXT_ID);                   // launch + ticket
}

The actual helper uses legacy IoReq objects rather than the shorthand above. Its request is stack-allocated safely because the iDMA control front end always completes these 32-bit register accesses synchronously with IO_REQ_OK.

The two fake memory behaviors

TCDM Synchronous source

The iDMA has already subtracted loc_base, so the callback indexes directly into local_memory, copies bytes, and returns IO_REQ_OK.

AXI Asynchronous destination

The callback copies data into axi_memory, retains the request, schedules the response event, and returns IO_REQ_PENDING.

Copying AXI data at acceptance while delaying the acknowledgment is intentional. It separates “the payload arrived” from “the DMA was told it completed,” which is exactly the distinction the faulty accounting loses.

Why the sizes matter

The first transfers are 48 and 64 bytes with a 32-byte transfer width. They become chunks:

Issue order:     A32, A16, B32, B32
Forced response: A32, B32, A16, B32

The key is that A has a 16-byte tail while B has a 32-byte chunk. If an implementation attributes every response to only the oldest or last remembered burst, B's 32-byte response is charged to the wrong remaining count. Unequal sizes turn a vague ordering mistake into deterministic counter corruption.

How response order is forced

static constexpr int forced_order[] = {0, 2, 1};
if (forced_response_step < 3)
{
    int index = forced_order[forced_response_step];
    if (index >= (int)pending_responses.size()) return -1;
    forced_response_step++;
    return index;
}

The callback waits until the requested index exists. It does not assume B's first request has already arrived. This makes the test deterministic even if model scheduling shifts slightly.

Phase-by-phase execution

PhaseTester actionExpected iDMA effect
1Submit 48-byte A; verify returned ticket is 1.Reserve logical burst A; issue A32 and A16.
2Submit 64-byte B; verify ticket 2.Reserve logical burst B; issue B32 and B32.
3Submit 32-byte C; verify ticket 3.C may wait upstream until an AXI burst slot becomes free.
4Respond A32, then B32, then A16.A and B accounting must follow request ownership, not response order.
5Drain remaining responses and poll DONE_ID.A and B release both slots; C runs; DONE_ID reaches 3.
6Compare the three destination ranges.Every byte matches its deterministic TCDM source.

The exact cycles are intentionally not asserted. The test checks ordering and eventual progress without coupling itself to incidental internal scheduling latency.

Why three descriptors are required

A test that submits only the first two transfers could stop after observing that bytes reached memory. But the defect leaks burst slots. A third descriptor asks the stronger question: did the previous transfers finish cleanly enough for the engine to continue?

The architectural oracle

uint32_t done_id = 0;
register_access(IDMA_DONE_ID, false, done_id);

if (done_id >= 3)
{
    check_result();
    return;
}

DONE_ID is the software-visible completion state. Requiring it to reach ticket 3 directly captures the reported failure: some sends never become done. Then check_result() verifies that every destination range matches its source.

Why the event callback is empty

The event port is bound so the DUT has its normal completion output, but event_sync() deliberately does not declare success. Events are broadcast notifications and do not carry a ticket. The test polls DONE_ID to prove which descriptor completed, just as software must consult architectural state.

Every way the test can finish

  • A wrong or rejected ticket fails immediately.
  • A failed DONE_ID register read fails immediately.
  • Destination data mismatch fails after ticket 3 completes.
  • No ticket-3 progress by cycle 200 fails with the last done ID and AXI request count.
  • Only ticket 3 plus matching data prints the exact PASS line and calls quit(0).

Red and green

Before the fix

(done_id=2, AXI requests=4)

The deterministic failure is the desired “red” regression state.

After the fix

14. gvtest and testsets

gvrun runs one selected target. gvtest organizes many tests: it discovers testset files, runs their build and execution commands, limits shared resources, captures logs, and invokes checkers.

The testset is executable Python

def testset_build(testset):
    testset.set_name('idma')
    testset.set_components(['pulp.idma.reg32_3d_dma'])

    test = testset.new_make_test(
        'axi_write_response_reordering',
        checker=_check,
        build_resource='gvsoc.core.build',
        no_clean=True,
    )

The name identifies the suite and test. The component list helps classification and filtering. new_make_test tells gvtest to use the directory's Makefile.

Why a checker exists when the process has an exit code

A checker makes the expected semantic result explicit and catches cases such as an early exit, crash, or command that never ran the intended model.

PASS_RX = re.compile(
    r'^\[\d+\] tester PASS done_id=3 reordered_responses=1$',
    re.MULTILINE)

def _check(test, output, *args, **kwargs):
    if PASS_RX.search(output):
        return True, 'all three tickets completed'
    ...
    return False, 'no tester PASS / FAIL line in output'

Shared build resources

build_resource='gvsoc.core.build' prevents parallel tests from colliding while they update the same GVSOC build/install tree. no_clean=True avoids cleaning a shared build that other tests depend on. These are orchestration concerns, not simulated-hardware behavior.

Suite discovery

A parent testset.cfg imports child testsets. Adding the iDMA directory to the parent suite makes CI and developers discover it without knowing its exact path.

15. A working build–run–suite workflow

Build the model and test target

In this embedded checkout, run the build from the actual GVSOC root and pass the test directory as a module root:

cd /home/ivan/repos/magia-sdk-v3/gvsoc

make TARGETS=test \
  MODULES=/home/ivan/repos/magia-sdk-v3/gvsoc/pulp/tests/idma \
  build

TARGETS=test selects the test target for generation. MODULES=... lets the build discover and compile the test's C++ source and import its Python generator.

Run it directly

mkdir -p /tmp/gvsoc-idma-regression

install/bin/gvrun \
  --target-dir=/home/ivan/repos/magia-sdk-v3/gvsoc/pulp/tests/idma \
  --target=test \
  --work-dir=/tmp/gvsoc-idma-regression \
  run

The explicit work directory keeps generated runtime files away from source. While the vulnerability is present, an exit status of 1 and the ticket-3 timeout are expected. After the model fix, this same command must exit 0.

Run through the suite

The precise gvtest command depends on the environment setup used by this checkout. Ask the installed executable for its current options rather than relying on an old invocation:

gvtest --help
gvtest --testset /home/ivan/repos/magia-sdk-v3/gvsoc/pulp/tests/testset.cfg tests

The small test Makefile assumes the usual standalone repository layout via GVSOC_ROOT ?= ../../../... Here GVSOC is embedded inside a larger SDK, so that default may point at the SDK root instead of the GVSOC root. Override GVSOC_ROOT or use the verified root-level commands above.

Read failures in layers

  1. Generation failure: Python imports, target discovery, properties, or bindings.
  2. Build failure: C++ syntax, includes, model discovery, linking, or installation.
  3. Startup failure: shared-library loading, factory symbol, port binding, or configuration.
  4. Behavioral failure: the model ran and the test's assertion or timeout fired.
  5. Suite-only failure: Makefile, checker, path discovery, environment, or resource orchestration.

16. Debugging habits and common pitfalls

Inspect structure before behavior

Use the tree command to verify component names, parameters, and hierarchy. Use diagram when bindings are hard to visualize. If the graph is wrong, no amount of C++ tracing will make the runtime behavior right.

Print state that explains the failure

A message like “timeout” is weak. The iDMA test reports the last DONE_ID and number of issued AXI requests. Those values distinguish “nothing started” from “two completed and the third starved.”

Do not accidentally serialize an ordering test

If a fake AXI target returns OK, every request completes during the call and there is no opportunity to reorder responses. To test interleaving, retain multiple requests with PENDING, then respond later in an intentional sequence.

Watch ownership at asynchronous boundaries

  • Do not store a pointer to a stack request if the caller may return or reuse it.
  • Do not access a request after calling its response callback.
  • Track which requests have already received responses.
  • Do not confuse “data copied into fake memory” with “transaction acknowledged.”

Keep the oracle public

Checking a private internal queue can make a test brittle and can accidentally encode the faulty implementation. Prefer registers, output interfaces, data memory, interrupt/event behavior, and the process exit status.

Make scheduling assumptions explicit

If the test needs request 2 before sending a response, check that it exists and retry next cycle. Never index a queue based solely on an assumed callback order.

A quick pre-PR checklist

  • The regression fails on the parent commit for the intended reason.
  • It passes with the fix repeatedly.
  • The direct command and suite command both work.
  • No application SDK is needed to trigger a model-level defect.
  • Comments explain why unusual sizes and ordering are necessary.
  • The timeout is long enough for a correct model and short enough for CI.
  • The test leaves generated artifacts outside the source directory where practical.
  • The parent testset imports the new child testset.

17. Compact glossary

Binding
A connection between compatible master and slave ports.
DUT
Device under test; here, the legacy register-programmed 3D iDMA.
Elaboration
Executing Python generators to construct and configure the system tree.
FSM
Finite-state machine; a common way to organize a component or testbench across events.
Generator
Python code that describes a target or component hierarchy.
Oracle
The rule a test uses to decide whether observed behavior is correct.
Pending request
An accepted IO request whose completion callback will happen later.
Response interleaving
Responses from different requests or bursts appearing in an order that is not simply the original issue order.
Ticket / done ID
Software-visible IDs used to identify submitted work and completed work.
Work directory
The directory where a run places generated configuration and runtime artifacts.

If you remember only five things: Python builds the hierarchy; C++ implements behavior; masters initiate and slaves handle; pending IO requires a later response with careful lifetime management; and a good model regression tests public behavior with a deterministic timeout.
